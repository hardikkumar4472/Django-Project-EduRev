# PROJECT PURPOSE

Build an official university platform for **post-allocation hostel room exchanges**.

Students should no longer need to coordinate room changes through WhatsApp, informal requests or manual paperwork.

The platform should handle the complete lifecycle:

STUDENT REQUEST
↓
ELIGIBILITY VALIDATION
↓
MATCH DISCOVERY
↓
DIRECT SWAP / MULTI-PARTY CYCLE
↓
PROPOSAL

↓
WARDEN APPROVAL
↓
ATOMIC OCCUPANCY UPDATE
↓
TRANSFER RECORD
↓
AUDIT TRAIL
↓
NOTIFICATIONS

The application must be designed as a serious university system rather than a student CRUD project.

---

# CRITICAL BUSINESS RULE

The most important technical requirement is:

## NO PARTIAL ROOM TRANSFER

If a 4-person exchange is approved, either:

ALL 4 room allocations change successfully

OR

NONE of them change.

There must never be a partially completed rotation.

PostgreSQL transactions and row-level locking must enforce this.

# PHASE 14 — TRANSACTIONAL OCCUPANCY UPDATE

THIS IS THE MOST IMPORTANT BACKEND PHASE.

Use PostgreSQL:

transaction.atomic()

and:

select_for_update()

When executing a multi-party transfer:

1. Validate proposal again.
2. Validate every participant.
3. Validate all beds.
4. Collect every affected bed.
5. Sort beds by primary key.
6. Lock them in that fixed order.
7. Re-check occupancy.
8. Update all beds.
9. Update student allocation records.
10. Create TransferRecord.
11. Create AuditEntry.
12. Commit.

If any operation fails:

ROLLBACK EVERYTHING.

No partial room movement.

Example:

4-party chain:

A: Bed 101 → Bed 203
B: Bed 203 → Bed 304
C: Bed 304 → Bed 412
D: Bed 412 → Bed 101

The transaction must update all four allocations atomically.

The fixed lock ordering is essential.

Document this in:

docs/locking-strategy.md

Explain:

* Why rows are locked
* Why ordering is required
* How deadlocks are reduced/prevented
* Why partial transfers cannot occur
* What happens when occupancy changed before approval
